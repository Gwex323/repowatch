# P1 本地控制 API 与界面

日期：2026-11-04。范围：3.6—3.7 的 API、安全会话与最小人工处理界面。运行内核见[正式运行引擎](runtime.md)，凭据见[P1 供应商](providers.md)。

## 开发启动与边界

前置条件：已安装锁定开发依赖；API／Worker 使用同一绝对 `REPOWATCH_DATA_DIR`；首次运行先在所有写者停止时[显式迁移](persistence.md#显式迁移与重启)。以下命令从项目根目录运行，须已获相应开发运行授权：

```powershell
pnpm --dir frontend build
backend/.venv/Scripts/python.exe -m repowatch.api --port 8765
```

API 仅绑定 `127.0.0.1`，同源提供 `frontend/dist`。启动完成后浏览器通过 URL 片段接收一次引导凭证，前端立即移除片段；凭证不进入服务访问日志。API 不隐式迁移或启动 Worker，打开／刷新页面本身不领取重任务或发起模型请求；API 生命周期内的只读巡检见下方 P4 说明。另一个终端可显式启动 Worker：

```powershell
backend/.venv/Scripts/python.exe -m repowatch.worker
```

`--once` 只执行一次调度；Worker 先做异常对账。开发调试可使用终端中断；浏览器关闭不等于 Worker 已停止。P6 的 Windows 安装启动器和服务联动停止见[本地安装与运维](local-operations.md)，完整交付验收状态见 NOW。普通仓库扫描、修复与返修由独立 Worker 执行；只读同步不替代其串行执行、预算和证据门槛。

## 会话与控制路由

每次 API 启动只接受一次、10 分钟内有效的引导，建立 8 小时 HttpOnly、SameSite Strict 会话。所有 API 核对回环 peer、固定 Host 及允许 Origin；变更还必须带会话防跨站令牌。Uvicorn 不信任代理头。错误使用固定分类，不回显提交内容、密钥或原始 SDK 正文；配置、事件与受控日志使用统一脱敏。

`/api/v1` 下提供状态、任务详情、供应商整批导入／手工编辑／显式列表、角色绑定、暂停／显式恢复、补充信息／配置／优先级、独立诊断、初始预算／有限加额／续期决定、阻塞处理和旧运行报告／放弃入口。变更使用稳定操作标识及预期修订，重复回读原结果，过期或同标识不同内容拒绝。模型诊断只登记意图，由 Worker 取得执行位后执行；显式模型列表为有界只读请求。

## GitHub 账号与仓库登记

在「设置与维护 → GitHub 账号」输入 GitHub 用户名和个人访问令牌（PAT），验证后保存。首个账号会设为默认，可在账号列表切换默认、重新验证、更换令牌或解绑。令牌保存在 Windows 凭据库，备份不包含令牌。更换令牌须属于同一个 GitHub 用户；在 GitHub 改名后，重新验证可更新列表显示，既有仓库如因身份不符阻塞，需重新预检。

在「仓库」页粘贴上游 GitHub 仓库首页链接（如 `https://github.com/owner/repository`），也可使用以 `.git` 结尾的 HTTPS 克隆链接。目标分支另填。新登记会预选默认账号和「发布 PR 时自动选择」。预检只读取仓库和目标分支，所以没有上游推送权限、还没有 Fork 也能登记可读取的公开仓库。已有的直接分支或指定 Fork 配置仍可沿用。

Issue 按上游的 Issues 设置和所选账号权限独立处理。获准发布 PR 时，有上游推送权限就用上游分支；否则核对、复用或创建执行账号自己的 Fork。Fork 尚未就绪或结果未知时，到 GitHub 核对后再按任务提示重试，系统不会盲目重发创建，也不会自动合并 PR。

点击「登记仓库」即完成预检和登记，使用默认准入与扫描策略。可在仓库条目的「编辑仓库配置」中按需展开「准入与扫描策略」。切换默认账号不会改动已有仓库；如需改绑，在该仓库的编辑表单中选账号并保存。仍有仓库引用的账号不能直接解绑；本地解绑也不等同于在 GitHub 撤销令牌。

仓库配置中的「从工作台移除」只隐藏本地仓库入口并暂停其后续任务与只读同步。GitHub 远端、Issue、PR、历史任务和审计证据均保留；再次登记同一仓库可恢复显示并创建新的导入扫描。

## 人工处理与事件恢复

首页按仓库展示进度；仓库内从「概览、分析、问题与修复、配置」进入相应工作。扫描发现可查看证据并进入已关联的 Issue；查重不能确定关系时展示判断依据。任务详情将修复证据与 PR 交付状态分开，另保留固化输入、预算、进展、日志和旧运行的操作入口。全局「待我处理」展示阻塞原因、失败步骤与处理建议。用户处理后点击「已解决，重新检查」，无需填写说明；系统检查已知环境条件、旧执行、远端操作及预算，保存依据与有限重试授权，全部阻塞解决且恢复条件满足时恢复队列。检查失败更新原因并保留阻塞。未知历史错误显示记录缺失，待重新检查或受管执行生成新的诊断。

预算区区分预警、正常续期与耗尽；显示实际、预留及未知占用。有限续期可以批准、改额度、拒绝、取消或刷新过期依据。独立人工加额绑定当前输入／进展／账本依据，可重新核对；不清零累计用量或窗口，不自动解除全局／仓库暂停及其他障碍。所有管理入口在暂停期间仍可用。

`/events` 提供持久游标分页，`/events/stream` 提供有界批次 SSE。事件帧 ID 是业务序号；浏览器断线以 `Last-Event-ID` 续读，每次重连重新校验会话。前端保存会话内游标并按序号去重，收到事件后回源读取业务状态；事件传输不承载任务执行。流关闭后浏览器按有限间隔重连，不长期占用数据库读事务。

## 验证入口

### P5 仓库记忆首批接入

2026-11-09，10.1 提供仓库记忆正文和不可变来源记录：症状、适用条件、方法、验证方式、限制，关联任务／运行／修复会话、base／候选 SHA 与原始产物路径／摘要。原始日志和代码仍保存在来源仓库的产物归档，不复制进正文。

认证后 `GET /api/v1/repositories/{repository_id}/memories` 可读取本仓记忆与来源；读取不调用模型或修改任务。成功状态仅从已验证、已独审且实际产物完整的来源创建；失败尝试单独保存，人工记录为 `manual_unverified`，提炼前收到新反馈则为 `pending_review`。PR 交付状态独立回读，不将合并当作代码验证。根因没有独立证据时须记录在限制中，不能因修复通过便标为已证实。

后续 P5 已接入串行自动提炼、FTS／本地 CPU 向量适配、反馈复核、独立记忆注入与逐请求检查；仓库配置中可查看、纠错、禁用、删除及确认去敏共享经验，全局设置中管理索引。原始来源和正文历史保留，删除立即停止未来复用；管理操作不隐式调用远端模型。完整约束、资产准备及 E10／E12／E16 复跑见[记忆生命周期与检索](memory.md)，数据库要求见[持久化说明](persistence.md#显式迁移与重启)。本轮只使用临时测试数据，未迁移用户数据。

### P4 持续同步与 PR 评审返修

2026-11-09：API 生命周期管理单个只读同步循环，独立持久租约与 Worker 执行位分离。正式导入后的仓库默认活跃 2 小时、空闲 24 小时同步，最近变化回看为 7 天；可在仓库的“巡检与必要 CI 检查配置”调整。未结束任务、开放受管 PR 或回看内实际变化形成活跃判定；相同载荷不刷新变化时间。PR、CI、评审共用该频率，没有额外分钟级远端轮询。

仓库“检查更新”调用 `POST /api/v1/repositories/{repository_id}/sync`，使用现有安全会话及稳定 `operation_id`；`GET` 同路径回读请求／完成序号、最后成功时间、目标 SHA、无变化／变化／失败及退避状态。配置保存使用 `POST .../sync/configure` 与独立策略修订。读取前的触发合并，读取中到达的新请求保留后续读取。暂停期间同步仍可保存变化并登记扫描，扫描等待恢复；不增加导入代次或重置预算，同版本已排队扫描可复用。

Issue 列表按完整分页、远端 `updated_at` 水位、重叠窗口和周期全量复核读取；评论、PR、reviews、checks、statuses、分支及分支规则使用各自端点和独立验证器。单页 304 不结束完整查询，分支缓存与已确认 SHA 不对应时无条件重读。对象、修订、信号和事件原子保存；较旧／同时间戳冲突保留不确定性并重读，旧同步及旧目标配置不覆盖新状态。网络／限流失败保留成功记录，尊重退避，不自行调用模型或解除暂停。重启仅补偿一次到期仓库；活进程尚在时不因租约超时抢占，退出等待当前有界读取后关闭存储。

任务详情显示受管 PR、Issue、代码验证及 CI 的独立事实，以及检查来源、对应 head／base／merge SHA 和 attempt。当前 base 以独立分支读取为准，PR 的历史 base 字段不能替代当前目标；merge 检查还须核对提交父节点包含当前 head 和 base。必要检查来自已确认的版本化配置及可读取的分支规则；来源未确认、缺失、pending、Fork 待批准、旧 SHA 或默认 skipped／neutral 均不算成功。只有明确策略才允许额外成功结论。示例必要检查：`[{"name":"tests","source":"123","kind":"check","ref":"head","accepted":["success"]}]`；`source` 为 GitHub App ID，传统 status 则填写发布者登录名。

评审意见由原任务的 Worker 串行分析，保存对应提交、撤销／旧代码状态和范围依据。明确原范围内的意见自动排队；原批准内容未变时新增验收修订并关联原批准及不可变分析产物，不修改旧历史。扩展或歧义在任务详情展示意见、方案和验收差异，提供批准、要求修改、补充澄清、拒绝四个入口；旧决定不适用于新反馈。批准不会解除暂停或绕过扫描／证据门槛。

返修抓取最新 PR head，在保留外部提交的前提下整合当前 base；冲突进入 `pr_merge_conflict` 等待，由用户在原分支处理后检查更新、重新分诊。复现基准与完整 PR 的当前 base 回归基准分别记录，仍需真实 Runner 和独审，更新同一个 PR并使用实际旧 head 的版本保护。发布前独立重读受管 PR 评审，期间的新意见使旧输入重新分诊。PR 合并、关闭未合并和 Issue 状态分别保存，不自动合并、重开或创建替代 PR。

复跑入口：`test_github_sync.py`、`test_github_polling.py`、`test_pr_lifecycle.py`、`test_issue_context.py`、`test_publication.py` 和启用 `REPOWATCH_DOCKER_TESTS=1` 的 `test_repairs.py`；浏览器入口 `node experiments/p4-browser.mjs` 使用临时库、模拟 HTTP 和无头 Edge。端点契约参照 [GitHub Issue API](https://docs.github.com/en/rest/issues/issues)、[分支规则 API](https://docs.github.com/en/rest/repos/rules)和[分支保护 API](https://docs.github.com/en/rest/branches/branch-protection)。实际本轮结果以 [NOW](../context/NOW.md#证据入口与时效) 为准。

真实 9.5 入口为 `experiments/p4-github-acceptance.py`，复用两套受控 P3 验收库、凭据引用、Issue／PR 与累计预算；显式区分迁移、评审、同步、返修、暂停及操作者终态，模型使用离线夹具。用户授权的 #16／#18 请求修改及原 PR 返修已完成；验收操作者合并 #16、关闭未合并的 #18，产品同步分别记录 `pr_merged`／`pr_closed_unmerged`。#18 的原分支冲突经用户授权解决并验证。两仓 CI policy 按用户确认无 required checks。范围与验证时效见 [NOW](../context/NOW.md)。入口不会自行决定重试或自动合并／关闭。

### P3 分诊与验收规范首批接入

2026-11-06 接入 P3 分诊和修复协调器。Worker 对已确认 Issue 和选中的扫描候选进行宿主准入复核，再通过共享引擎的 `investigate` 模式读取输入、保存结构化分析及分诊结果。手动未选择、标签模式未命中或允许标签未配置的 Issue 不自动调用模型；明确选择仍不能覆盖他人 assignee、排除标签或敏感披露判断。初诊缺信息与敏感披露进入正常等待，不因此暂停全局队列。远端读取包含 Issue、完整分页评论、开放 PR 与 timeline 关联 PR 的描述和文件差异；占用及关系判断保留证据。当前仍有专项／真实 GitHub 验收缺口，不能据接口存在宣称整个 P3 通过。

任务详情可查看分诊原因、证据及输入／准入修订，使用“请求接手并重新核验占用”保存意图；请求不会修改远端 assignee。分诊可生成待确认的方案与验收规范，用户也可保存新修订并明确批准。规范 JSON 包含 `objective` 和非空 `criteria` 列表；功能／重构包含 `plan`，纯重构另含 `structural_goal` 与 `behavior_preservation`。内容历史不可覆盖或删除，批准绑定输入、相关反馈、准入策略及目标配置；目标 SHA 单独变化不作废批准。上述版本变化后须重新绑定规范，普通批准不重新启用取消／排除任务，也不解除暂停或执行障碍。

批准后返回原任务分诊，仍须核对当前准入及后续 Issue／PR、扫描、复现和发布门槛。多个独立目标须先收敛／拆分，不能靠批准原多目标列表合并交付。模型分析只说明信息与目标是否充分，不构成实际修改前失败／修改后通过证据。当前 schema 要求见[显式迁移](persistence.md#显式迁移与重启)，现有开发数据库须在全部写者停止后显式迁移；测试只迁移临时数据，不隐式升级用户数据库。

专项测试为 `test_triage.py`、`test_formal_triage.py`、`test_acceptance_migration.py` 及任务／API／Worker 的关联回归。浏览器入口 `node experiments/p3-browser.mjs` 使用临时回环服务和 Edge，验证保存、批准、刷新持久化、输入变化失效、暂停可操作及读取不启动任务；报告位于 `.cache/p3-browser/`。SDK 测试使用模拟 HTTP，不代表真实付费调用或 GitHub 写入验收，最新结果见 [NOW](../context/NOW.md#证据入口与时效)。

### P3 修复证据与受控发布

任务详情显示冻结候选的实际内容摘要、修改前后探针结果、回归比较、独审运行及发布意图。Bug／功能须用同一探针取得 base 目标失败与候选通过；纯重构另保存结构目标和前后行为保持命令。缺包、超时、发现数量减少、新 skip、失败身份或原因变化均不能充作通过。最终候选停止处理工具写入，未提交或未跟踪源码变化使原证据失效。处理—Runner—独审按串行阶段交接，独审只能读证据或申请隔离补查。

可修复失败在原预算中循环；每轮完整验证记录一次进展比较，模型规划／实现／审查子阶段不各自消耗无进展次数。有效复现、不同子问题修复和最终候选有不可变产物依据；重复失败达到阈值全局暂停。查看原始日志和指纹后可补充信息／环境、取消、调整有限预算及通过已有阻塞处理与显式恢复入口重试；批准或加额不能代替验证。纯重构行为证据和探针独审引用保存在最终证据包中。

本地候选先完整查重，结果明确无相似才创建 Issue，确认相同则复用原主任务。创建结果未知时先按稳定标记和创建者对账，不按标题重发；新建 Issue 主任务继承候选的预算归属和执行配置。敏感候选停在脱敏待办。查重不明时在分诊依据中查看候选列表，填写补充信息作为依据后使用“关联已确认相同 Issue”或“确认完整查重无相似 Issue”；决定绑定当前查重版本，执行时仍重新读取。

“远端占用与 PR 关系核对”展示评论与 PR 对照，允许确认同一问题、无关、他人处理中或无占用。人工决定及其依据可回读，远端变化后失效。外部同问题开放 PR 正常等待；已合并时核实 merge commit 在目标分支历史中，使用最新扫描和真实探针确认，已解决记录 `externally_resolved`，仍有目标失败才继续原任务。关系或证据不确定不会发布。

发布器使用稳定受管分支、预期旧 SHA 和冻结候选，分别核对上游／发布仓库身份，保留原 PR 唯一绑定。正文含五段结构、单一 Issue 关闭声明、候选来源、验证摘要与 CI 未执行限制，不公开探针源码。默认不 assign／评论；认领评论须仓库策略显式开启，并保存意图与回执。PR 回执未知可用“请求核对远端回执”排队只读核对；按标记、创建者、仓库、分支及 SHA 唯一匹配，不能盲目重发。已关闭受管 PR 不释放绑定或另建。

认领评论只有在本地发布意图已确认、评论 ID／作者／完整正文匹配且未编辑时，才从外部反馈比较和上下文摘要中排除；实际读取结果仍保留该评论。发评后的重读不会增加反馈修订或使功能／重构的当前批准失效。其他新评论、伪造标记或认领评论被编辑仍须重新分诊。`test_claim_comments.py` 覆盖这些边界，`test_repairs.py` 的 `claim` 三种场景覆盖真实 Docker 修复流程。
