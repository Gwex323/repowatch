# Spec Delta

## Purpose

为本地单用户提供可复用的 GitHub 执行身份，使多个仓库可以使用同一已核实账号，并且仍各自保留所选账号、贡献路径和独立的授权检查。

## ADDED Requirements

### Requirement: 核验并管理 GitHub 账号
系统 SHALL 以 GitHub 返回的数字用户 ID 识别账号，支持保存多个账号、重验、更换同账号的令牌、设置默认和解绑。令牌 MUST 仅保存在宿主凭据库中，不出现在业务库、响应、日志或任务材料中。

#### Scenario: 首次绑定
- **WHEN** 用户提交用户名和属于该账号的有效 PAT
- **THEN** 系统保存账号并将首次绑定的账号设为默认

#### Scenario: 更换为不同身份的令牌
- **WHEN** 新令牌的数字用户 ID 与现有绑定不同
- **THEN** 系统拒绝更换并保留旧绑定

#### Scenario: 账号仍被引用
- **WHEN** 用户尝试解绑一个仍被已登记仓库使用的账号
- **THEN** 系统拒绝解绑并提示先改绑相关仓库

### Requirement: 仓库固定使用确认的账号
系统 SHALL 为新仓库预选默认账号，允许显式选择其他账号，并在保存前核验所选账号和目标仓库读取权限。既有仓库 SHALL 保持已保存的账号或旧凭据引用，直至用户通过预检确认改绑。

#### Scenario: 连续登记两个仓库
- **WHEN** 默认账号有两个仓库所需的访问权限
- **THEN** 两次登记均可使用该账号且无需再次填写令牌或凭据引用

#### Scenario: 切换默认账号
- **WHEN** 用户更换默认账号
- **THEN** 新登记预选新默认账号，已登记仓库的执行身份保持不变

#### Scenario: 权限不足或凭据已更换
- **WHEN** 预检遇到权限不足，或凭据在预检后发生更换
- **THEN** 系统拒绝确认并说明应核对权限或重新预检，且不会回退到其他账号

### Requirement: 通过 GitHub 链接定位上游仓库
仓库登记界面 SHALL 接受 GitHub 仓库首页的 HTTPS 链接或 HTTPS 克隆链接作为上游定位输入，并在重新预检已有仓库时填回其链接。

#### Scenario: 粘贴仓库链接
- **WHEN** 用户输入合法的 GitHub 仓库链接并提交预检
- **THEN** 系统从链接取得所有者和仓库名，沿用已选账号及目标分支完成预检

#### Scenario: 链接不是仓库首页或克隆地址
- **WHEN** 用户提交其他站点链接或 GitHub 的 Issue、PR、分支等子页面链接
- **THEN** 界面提示填写仓库首页链接，且不提交预检

#### Scenario: 一次提交完成仓库登记
- **WHEN** 用户点击登记且仓库预检成功
- **THEN** 系统直接登记并建立扫描任务，新仓库使用默认策略，已有仓库保留其策略或应用用户主动编辑的策略

### Requirement: 在发布 PR 时自动确定贡献路径
可读取的公开仓库 SHALL 可在没有上游推送权限、没有现成 Fork 时登记和扫描。自动路径 SHALL 在受控 PR 发布时验证上游推送权限，必要时复用或创建同账号的 Fork。Issue 发布按自身权限核验。

#### Scenario: 不具备公开上游推送权限
- **WHEN** 执行账号可读取第三方公开仓库
- **THEN** 系统允许登记和扫描，不创建 Fork

#### Scenario: 通过 Fork 发布
- **WHEN** 已通过发布门槛，上游允许 Fork 且当前账号不能推送到上游
- **THEN** 系统验证本人 Fork，缺失时登记请求并创建，核实关系和写权限后才推送并向上游提交 PR

#### Scenario: Fork 创建结果未知
- **WHEN** 已发送创建请求但尚不能确认结果
- **THEN** 系统只读核对，不重发创建，也不改投其他仓库
