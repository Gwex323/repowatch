# Design

## Context

现有宿主通过仓库配置的凭据引用读取 Windows 凭据库；参考项目集中绑定 PAT，并用 GitHub 数字用户 ID 区分账号。目标见 [提案](proposal.md)。

## Goals / Non-Goals

**Goals:** 将账号选择与仓库登记分开，沿用宿主保管凭据、仓库路径预检、真实交付门禁和本地会话保护。

**Non-Goals:** OAuth、自动申请仓库权限或自动改绑已登记仓库。

## Decisions

- 账号保留稳定内部引用，仓库继续保存凭据引用。宿主解析账号引用到当前已验证的令牌，仓库无需在换令牌时重写配置；默认选择只用于新登记表单。
- API 通过固定 GitHub REST 来源核对数字用户 ID。更换令牌先验证并写入新凭据，再提交新引用；过期预检在保存时按令牌引用检查。解绑在同一事务中检查仓库是否仍引用账号。
- 保留旧引用兼容路径。用户载入旧仓库并显式选择账号后，经现有预检和保存流程完成改绑。新令牌只进入现有 Windows 凭据库，沿用本地会话和请求来源校验。
- 登记页将固定 HTTPS GitHub 仓库链接解析为所有者和仓库名，沿用已有预检 API 和仓库稳定 ID；分支仍独立输入。
- 自动模式的登记只核验账号、仓库和目标分支，未选择发布仓库时不写入旧版直接／Fork 路径字段。旧配置仍可继续使用。Issue 按自身授权门槛处理。
- 发布 PR 时，重新核实账号和上游权限，有推送权限则使用上游；否则仅在公开仓库允许 Fork 时，核对本人同名 Fork，或在现有受控发布流程中登记事件并请求创建一次。结果未确认时只读核对。最终发布仓库写入 PR 意图，返修和对账沿用该意图。
- 登记按钮顺序调用现有预检和导入 API。新仓库使用后端默认策略；重复登记沿用已保存策略，已有仓库可在编辑表单按需展开并修改。
- 供应商模型列表复用同一个有界 `GET /models` 适配，由新增／编辑模型框的下拉按钮触发；草稿读取不保存配置，手填仍可用。角色页固定编辑处理和审查两个绑定，只读取所选供应商配置里已保存的模型，不请求远端列表。

## Risks / Trade-offs

- 身份已验证不代表仓库权限足够：逐仓库预检，实际写入仍由现有门禁复核。
- 数据库与凭据库无法在一个事务内提交：先写未激活的新令牌，再切换引用；失败时不替换当前凭据。恢复到另一数据目录时需重新提供对应账号的令牌。

## Migration Plan

通过现有显式迁移入口新增账号表，保留旧仓库行和原引用。回退旧版时使用迁移前兼容备份。
