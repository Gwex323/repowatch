## Context

实现基线包含 P6 和 GitHub 账号绑定。扫描查询提供当前版本、覆盖证据和历史批次；发现的处理请求在 Issue 确认后指向已有或新建的正式主任务。PR 状态及本地验证证据各有持久来源。仓库首页使用轻量的读投影；进入仓库后按需读取已核验的扫描详情。

## Goals / Non-Goals

- 以实际用户任务判断覆盖：能找到入口、读懂证据、完成对应操作并看到结果。
- 优先正文可读、对齐的圆角分栏和窄屏单列。文件路径、完整 SHA 和原始记录进入详情。
- 保留模型、账号、记忆、诊断、维护及人工控制的原有语义；不引入页面打开即执行任务或远端写入。

## Decisions

1. 首页采用已确认原型的「进度一览」。仓库内提供概览、分析、问题与修复、配置；全局待办按真实可操作事项汇总，可定位单一仓库。账号、模型、记忆索引和维护归入全局设置；仓库记忆在仓库中管理。
2. 扫描当前目标与最近已验证批次并列。排除与缺口分开，读历史证据不表示当前目标就绪。已确认的发现直接显示 Issue 编号；只在确有查重判断记录时提示待确认，不把查询全集都称为相似项。
3. 已核验的修复按复现、修改、验证、独审展示；PR 另列交付、CI 与远端评审。审批、核对和恢复仍由现有端点按修订和持久记录执行。
4. 已确认的整体验收保留两个关口。新增后端操作另按[交付契约](../../../docs/implementation-contracts.md#issue-与-pr-一一对应)验收，尤其是多目标 Issue 的范围确认、查重、各自独立交付与不擅自改原 Issue。

## Risks / Trade-offs

- 首页摘要以持久状态为准；扫描证据可读性只由扫描详情核验，不能把摘要当作当前就绪。
- GitHub Issue 与 PR 验收仍要区分本地夹具、真实受控技术验收和最终产品签收。
